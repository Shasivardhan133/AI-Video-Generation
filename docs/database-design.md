# Database design proposal

This document proposes metadata tables only. It does not create MySQL tables, Django models, or migrations.

## `users` (when accounts are implemented)

| Field | Purpose |
|---|---|
| `id` | Stable primary key, preferably a non-guessable UUID or Django-managed key. |
| `email` | Unique login/contact identifier if email authentication is selected. |
| `password_hash` | Managed by Django's authentication system; never store plaintext passwords. |
| `is_active` | Allows access to be disabled without deleting history. |
| `created_at`, `updated_at` | UTC lifecycle timestamps. |

Generation records should reference the user with a foreign key and an explicit deletion policy. The policy must not accidentally expose or orphan private output files.

## `generation_jobs`

| Field | Purpose |
|---|---|
| `id` | Primary job identifier, preferably a UUID suitable for API responses. |
| `user_id` | Foreign key to `users` when authentication is enabled; nullable only if anonymous jobs are intentionally supported. |
| `mode` | `text_to_video` or `image_to_video`. |
| `prompt_text` | The submitted or normalized prompt, subject to privacy and retention policy. |
| `status` | `accepted`, `queued`, `processing`, `completed`, or `failed`; `cancelled` only when implemented. |
| `input_storage_ref` | Reference to the uploaded image when applicable; not image bytes. |
| `output_storage_ref` | Reference to the generated video when completed; not video bytes. |
| `error_code` | Stable internal category for diagnostics. |
| `error_message` | Safe user-facing failure explanation. |
| `created_at`, `started_at`, `completed_at`, `updated_at` | UTC timestamps for lifecycle and auditing. |

Recommended indexes are `(user_id, created_at)`, `(status, created_at)`, and a unique index on the public job ID if a separate internal key is used. Indexes should be confirmed against real query plans.

## `generation_settings` (optional normalized extension)

Settings may initially be stored as a validated JSON object on `generation_jobs` to keep the first implementation understandable. If settings require querying, versioning, or enforcing relational constraints, use a related table:

| Field | Purpose |
|---|---|
| `id` | Primary key. |
| `generation_job_id` | Unique foreign key to the job. |
| `model_profile` | Application-owned name for a tested model configuration. |
| `width`, `height`, `frame_count`, `fps` | Validated supported output controls. |
| `seed` | Optional reproducibility value. |
| `raw_settings_json` | Auditable normalized request settings if needed. |
| `created_at` | Creation timestamp. |

Do not expose arbitrary model parameters until they are validated and known to be safe and feasible.

## Relationships and retention

- One user can own many generation jobs.
- One generation job has zero or one settings record.
- A job can reference one input and one output storage object, depending on mode and state.
- Foreign keys and deletion behavior must protect ownership boundaries.
- Retention and cleanup rules for inputs, outputs, and failed jobs must be defined before deployment.

All timestamps should be stored consistently in UTC. Status values should be represented by application constants/enums rather than repeated free-form strings. Database migrations will be generated by Django in a later phase.
